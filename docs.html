Quickstart

Five minutes end to end: append a record to a tamper-evident Merkle transparency log, verify the receipt with your network disconnected, and start a witness that checks every future checkpoint we publish. Everything below works on the free tier.

You will need an API key from the dashboard and a log name. Examples use the log acme-agents-prod.

1 · Install

The Python client ships both the library and the notary-witness command.

shell
pip install notary-client

Set your credentials in the environment so keys never land in source control.

shell
export NOTARY_BASE_URL="https://api.notary.dev"
export NOTARY_API_KEY="nk_live_8f3c…"

2 · Append a record

One call. The client canonicalizes the payload (RFC 8785 JSON Canonicalization), hashes the leaf, and returns a receipt containing the leaf hash, the index, the tree size it was integrated at, and the audit path needed for offline verification.

append.py
import os
from notary_client import NotaryClient

client = NotaryClient(
    base_url=os.environ["NOTARY_BASE_URL"],
    api_key=os.environ["NOTARY_API_KEY"],
    log="acme-agents-prod",
)

receipt = client.append({
    "actor":      "agent:refunds-v3",
    "action":     "issue_refund",
    "subject":    "order_88213",
    "amount_cents": 4200,
    "currency":   "USD",
    "approved_by": "policy:auto_under_5000",
    "occurred_at": "2026-08-11T14:22:09Z",
})

print(receipt.leaf_hash)   # 4d7f257e9da7f32989ead03cef9fbbb0…
print(receipt.index)       # 2481929
print(receipt.tree_size)   # 2481930

# Store the receipt next to your own record. It is the
# artifact an auditor verifies — keep it, not just the entry.
receipt.save("receipts/order_88213.notary.json")

Note

append() is safe to retry: pass idempotency_key= and a duplicate submission returns the original receipt instead of writing a second leaf.

3 · Verify the receipt offline

Verification is pure local computation. Hash the record, walk the audit path, compare the recomputed root against a checkpoint you already hold. No API call, no network, no trust in us.

verify.py
from notary_client import Receipt, Checkpoint, verify_inclusion

receipt    = Receipt.load("receipts/order_88213.notary.json")
checkpoint = Checkpoint.load("checkpoints/2481930.note")

result = verify_inclusion(
    record=open("records/order_88213.json", "rb").read(),
    receipt=receipt,
    checkpoint=checkpoint,
    # Ed25519 public key printed by `notary-witness init`.
    # Pin it once; it is what makes the check independent.
    log_public_key="notary.dev/acme+3f9c21ab+ASdW7pQ0…",
)

assert result.ok
print(result.summary)
# root 620d18e1…a3286f58 recomputed from leaf 2481929
# of 2481930 — matches signed checkpoint. verified offline.

The same check from the shell, for auditors who prefer an air-gapped machine:

shell
notary verify \
  --record     records/order_88213.json \
  --receipt    receipts/order_88213.notary.json \
  --checkpoint checkpoints/2481930.note \
  --log-key    notary.dev/acme+3f9c21ab+ASdW7pQ0… \
  --offline

# inclusion proof OK   index 2481929 / size 2481930
# note signature  OK   notary.dev/acme
# exit 0

4 · Run your own witness

This is the part that matters. notary-witness init generates an Ed25519 keypair on your machine and never transmits the private half. notary-witness watch then polls our checkpoints, demands a consistency proof against the last checkpoint it accepted, verifies that proof locally, and co-signs only if it holds.

shell
notary-witness init \
  --log acme-agents-prod \
  --state ./witness-state \
  --key-file ./witness-state/witness.key   # or --kms aws:alias/notary-witness

# witness key   ed25519:local/acme+8b92e  (private key stays here)
# log key       notary.dev/acme+3f9c21ab+ASdW7pQ0…  (pinned)
# baseline      size 2481904  root 74f4e8ea…eb79332f
shell
notary-witness watch \
  --log acme-agents-prod \
  --state ./witness-state \
  --interval 5m \
  --evidence-dir ./evidence

[10:42:01] checkpoint 2481930  consistency 2481904 → 2481930  OK  co-signed
[10:47:01] checkpoint 2481958  consistency 2481930 → 2481958  OK  co-signed
[10:57:14] checkpoint 2482006  consistency FAILED
           old root not derivable — REFUSING TO CO-SIGN
           evidence/2026-08-11T10-57-14Z.split.json  (exit 3)

Operational requirement

A witness that isn't running proves nothing. Run watch as a supervised service, alert on non-zero exit, and keep --state on durable storage — it holds the history the proof is checked against.

Hash-only privacy mode

On Team and Regulated, the client hashes locally and sends only the digest. We never receive the record body. Proofs, checkpoints, and witness co-signing are unchanged, because the log only ever needed the hash.

hash_only.py
client = NotaryClient(
    base_url=os.environ["NOTARY_BASE_URL"],
    api_key=os.environ["NOTARY_API_KEY"],
    log="acme-phi-audit",
    hash_only=True,               # only sha256(canonical_json) leaves the process
    metadata_fields=["action"],   # optional non-sensitive fields kept in the clear
)

receipt = client.append({
    "actor": "agent:intake-v2",
    "action": "read_chart",
    "patient_ref": "mrn:88213",   # hashed locally, never sent
    "occurred_at": "2026-08-11T14:22:09Z",
})

Checkpoint format

Checkpoints are C2SP signed notes: an origin line, the tree size, the base64 root hash, a blank line, then one or more signature lines. Plain text on purpose — a human can read it, and a 30-line script can verify it.

checkpoints/2481930.note
notary.dev/acme-agents-prod
2481930
Yg0Y4VoCent6/O4Hn+5ys59tevQFTqyVC9PISjKGb1g=

— notary.dev/acme P8lRqxCg5io2NorYJFiN3E9dOgpepDeZ6y2ZoQEk1cyx/0Cw96hEk8fteZYtNX8sQqQzX6TnezD6Sn86rl2oshPwqrw=
— witness local/acme LtQkWT5yRMMMgz5dk0QTfQEU75aDvxyC34MnuLTGZm0J5OzgQ/4cJa/ytT5aBKNvqRKOuny/ynZM2FiwNLVGd9YA=

The second signature line is yours. Its presence is your own past statement that the history was consistent at that size — which is why a later contradiction is provable without our cooperation.

HTTP API

Every client operation is a plain HTTP call if you'd rather not use the library.

EndpointMethodReturns
/v1/logs/{log}/entriesPOSTAppends a record (or a digest in hash-only mode); returns a receipt with leaf hash, index, tree size, and audit path.
/v1/logs/{log}/checkpointGETThe latest C2SP signed note for the log.
/v1/logs/{log}/proof/inclusionGETAudit path for a leaf index against a given tree size.
/v1/logs/{log}/proof/consistencyGETProof that tree size m is a prefix of tree size n. This is what the witness demands.
/v1/logs/{log}/witnessesPOSTSubmits a witness co-signature for a checkpoint.
/v1/logs/{log}/anchorsGETOpenTimestamps attestations for archived checkpoints (Regulated).

CLI reference

CommandPurpose
notary-witness initGenerate the witness keypair, pin the log's public key, record a baseline checkpoint.
notary-witness watchPoll, verify consistency, co-sign or refuse. Exit 3 on refusal, exit 4 on unreachable log.
notary-witness showPrint current witness state: last accepted size, root, and co-signature history.
notary verifyOffline inclusion-proof verification for a record, receipt, and checkpoint.
notary exportBundle records, receipts, checkpoints, and co-signatures into an auditor-ready archive.

Alerting and CI

Treat a refusal like a production incident, because it is one.

witness.service
[Unit]
Description=Notary witness (acme-agents-prod)

[Service]
ExecStart=/usr/local/bin/notary-witness watch \
  --log acme-agents-prod --state /var/lib/notary --interval 5m \
  --evidence-dir /var/lib/notary/evidence
Restart=always
RestartPreventExitStatus=3        # exit 3 = consistency failure: stop and page a human
User=notary

[Install]
WantedBy=multi-user.target

What this cannot do

A transparency log proves that everything in the log is intact. It cannot prove that everything that happened was written to it — omission at the boundary. If an agent acts and never calls append(), no proof downstream can surface a record that was never created.

Mitigate it where you can — append from inside the tool-execution path rather than a side channel, log the intent before the effect, and record heartbeat entries so a silent gap is visible as a gap. But understand the limit precisely: we make alterations to recorded history detectable by third parties. We make no claim to prevent alteration, we do not validate that a record is accurate, and we are not a substitute for a records-retention program.
